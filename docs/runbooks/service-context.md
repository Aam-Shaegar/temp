# Контекст конкретного TCP-сервиса

`network → Go-сенсор → feature windows → PostgreSQL → Python → журнал Go`

Сенсор может принять готовые пятисекундные агрегаты от доверенного экспортёра прокси или приложения. Пакетные признаки по-прежнему рассчитывает Go. Экспортёр считает ответы в окне по времени завершения запросов, а плановые операции получает из расписания, известного в момент анализа. Каждому сенсору и сервису выделяется свой каталог. Хост и контейнеры пользуются синхронизированным временем.

Запишите агрегат атомарной заменой файла `<window_start_ns>.json` после конца окна и до его выгрузки сенсором. Допуск опоздания (`NETWATCH_CAPTURE_LATENESS`) должен покрыть обычную задержку экспортёра. Храните агрегаты достаточно долго для планируемого replay. Поля передаются и для наблюдения с нулём ответов.

```json
{
  "schema_version": 1,
  "sensor_id": "api-a",
  "entity_id": "TCP/192.0.2.10:443",
  "window_start_ns": "1795000000000000000",
  "window_end_ns": "1795000005000000000",
  "completed_requests": 45,
  "server_errors": 2,
  "mean_latency_ms": 21.7,
  "planned_activity": false,
  "source_ref": "proxy:20261120.batch-042",
  "operations": [
    {
      "route_id": "reports.export",
      "method": "POST",
      "completed_requests": 9,
      "request_body_bytes": null,
      "response_body_bytes": 600000,
      "expected_requests": 8
    }
  ]
}
```

Для нуля ответов используйте `mean_latency_ms: null`. Если расписание неизвестно, передайте `planned_activity: null`. При отсутствии пригодного агрегата контекстная модель возвращает `insufficient_data` с причиной `application_context_missing`. Пакетный профиль продолжает использовать свои признаки. Буфер доставки фиксирует агрегат вместе с окном и повторно отправляет именно этот снимок.

`operations` можно опустить. Если поле передано, оно содержит от одной до 32 разных пар «идентификатор маршрута + HTTP-метод». Используйте стабильный ключ из конфигурации приложения, например `reports.export`, без исходного URI, параметров запроса и идентификаторов клиентов. Допустимые методы — `GET`, `HEAD`, `POST`, `PUT`, `DELETE`, `CONNECT`, `OPTIONS`, `TRACE`, `PATCH`. Считайте завершённые транзакции и суммарные размеры их тел в байтах по времени завершения. Если для части этих транзакций размер тела не известен, передайте `null` для соответствующего итога. `expected_requests` — ожидаемое число завершений по независимому расписанию или прогнозу, доступному к моменту наблюдения. При отсутствии такой оценки передайте `null`. Ноль означает измеренный ноль или явную оценку нулевого спроса. Сумма завершений по перечисленным операциям может быть меньше общей. Отсутствующий маршрут означает, что его агрегат не передан.

`source_ref` — необязательная непрозрачная ссылка на запись во внутреннем журнале оператора. Она сохраняется вместе с агрегатами в деталях инцидента. Передавайте только идентификатор без секретов, пользовательских данных и URL. Файл агрегата ограничен 16 КиБ, принимаются только показанные поля и соответствующие окну идентификаторы и время. Предыдущий формат из четырёх прикладных полей остаётся допустимым.

В Docker задайте `NETWATCH_APPLICATION_CONTEXT_DIR` в файле рабочего профиля и запускайте `COMPOSE_PROFILES=sensor make work WORK_CONTEXT=1`. Передавайте `WORK_CONTEXT=1` также при просмотре логов и остановке. Для нативного сенсора и replay предусмотрен флаг `--application-context-dir`.

Если экспортёр и сенсор работают от разных пользователей Linux, выделите им общую группу чтения. Назначьте экспортёру владельца каталога, выставьте группе права чтения и прохода и включите наследование группы каталога (`setgid`, режим `2750`). У экспортёра должны быть права записи в каталог и членство в группе. Укажите числовой GID группы в `NETWATCH_APPLICATION_CONTEXT_GID` и передайте тот же GID как `--group-id` при экспорте. Без `--group-id` новые файлы приватные (`0600`). С аргументом файлы получают `0640` до публикации, а сенсор читает их через дополнительную группу и монтирует каталог только для чтения. Для одного пользователя подходит приватный каталог.

## Теневой прогон

Соберите экспорт окон с полностью подтверждённым наблюдением и журналы приложения для разметки. Поднимите отдельный проект Compose со своим портом API и PostgreSQL. Для исторического прогона используйте `netwatch-sensor replay`, затем очередь и доставку во временный стек. Для живого прогона оператор задаёт выделенный сенсор и метрики именно этого сервиса. Источник телеметрии и проекты Compose выбираются при развёртывании.

Манифест `manifest.json` содержит `schema_version: 1`, `feature_set_version`, `binding` с `sensor_id` и `entity_id`, два массива `captures.train` и `captures.calibration`. Элемент массива содержит `source_sha256`, относительный путь `windows` до JSONL и `windows_sha256`. Каждая строка имеет `window` по контракту и `label` со значением `normal` или `anomaly`. Для обучения типизации укажите также `phase` (идентификатор группы последовательных окон внутри захвата) и `episode_label` из словаря классификатора или `unknown`. Присвойте фазе метку по разметке приложения и используйте для обучения окна, целиком попавшие в её интервал. Резервируйте другие захваты для финального прогона.

```sh
python3 scripts/stack.py train "$DATASET" "$MODEL_IF" --method isolation_forest --rules
python3 scripts/stack.py train "$DATASET" "$MODEL_MLP" --method mlp --rules
python3 scripts/stack.py train "$DATASET" "$CLASSIFIERS" --contextual-classifiers --method random_forest
```

Сравните оба детектора с одинаковыми правилами на одних записях. Правила проверяют измеренные ошибки и задержки HTTP, включая период плановой активности. Порог ML калибруется отдельно для окон с плановой активностью и без неё. Если для сервиса задан SLO, укажите в манифесте `application_limits` с полями `min_requests`, `server_error_fraction` и `latency_ms`. Иначе начальные границы рассчитываются по калибровочной выборке. С флагом `--network-only` обучается модель без прикладных агрегатов. Для объединённого журнала задайте `NETWATCH_POLICY_VERSION=v3`. Эта политика открывает инцидент после двух смежных сигналов и закрывает после двух штатных окон. При подтверждённом разрыве или недоступной оценке журнал фиксирует прерывание.

Измеряйте пропуски, неподтверждённые инциденты, начало, конец и задержку подтверждения. Для `make test-acceptance` зафиксируйте в манифесте `start_tolerance_s: 5`. Проверка использует пересечение с разметкой и допускает начало инцидента не более чем на одно окно раньше. Затем передайте полные непрерывные окна закрытых инцидентов классификатору из соответствующего артефакта той же командой `classify`, что и для сетевого профиля. Если наблюдения показывают прикладную деградацию, классификатор воздерживается от присвоения одного из известных сетевых типов. Решение о выпуске принимается после независимой проверки целевого сервиса.

## Сравнить каскады с Random Forest

Для обоих детекторов используйте один манифест и включите `--rules`. Параметр `threshold_mode: "confirmed_pairs"` калибрует пороги на смежных размеченных окнах. Параметр `separate_application_health: true` передаёт частоту ошибок и задержки HTTP независимому правилу. Оба детектора используют один набор правил. Метрики инцидентов считают на непрерывных отложенных записях.

Для новых кандидатов включите `threshold_mode: "incidents"`, `separate_application_health: true` и `independent_application_evidence: true`. К каждой записи `captures.calibration` добавьте относительный путь `timeline` и его SHA-256 в `timeline_sha256`. JSON по этому пути содержит `source_sha256` того же захвата, непрерывные `windows` и список `truth`. Каждая фаза `truth` имеет целочисленные `start` и `end` в наносекундах, `label` и `planned`. У подтверждённых сетевых событий укажите `evidence_channel: "network"`, у подтверждённых прикладных сбоев — `"http"`. Сохраняйте переходы и пропуски в `windows`. Go использует их при открытии, восстановлении и закрытии. Docker-тренер уже включает `netwatch-projection-driver`. Для нативного запуска соберите его командой `go build -o bin/netwatch-projection-driver ./benchmarks/projection-driver` и укажите `--projector bin/netwatch-projection-driver` модулю `netwatch_ml.training.service_detector`.

Для отдельного порога режима нужны минимум две калибровочные записи с пригодными штатными окнами и две записи с подтверждённым сетевым эпизодом, в котором есть два смежных пригодных окна. Расписание выбирает порог и не входит в числовые признаки новой модели. Необеспеченный данными режим получает `insufficient_data` и `regime_uncalibrated`. HTTP-правило остаётся самостоятельным. В отчёте обучения есть поддержка по режимам и измеренная экспозиция. Короткий период без тревог подходит для подбора кандидата и требует независимой проверки бюджета тревог. Артефакты нового режима обслуживаются под `NETWATCH_POLICY_VERSION=v4`.

Оба каскада используют один и тот же артефакт `random_forest.json` для данного сервиса. Сохраните JSON-ответ операторского `GET /v1/incidents/{id}` и проверьте SHA-256 модели по манифесту.

```sh
./scripts/uv run --project ml --locked python -m netwatch_ml.training.episode_classification \
  classify "$INCIDENT_JSON" "$CLASSIFIER_JSON" "$CLASSIFIER_SHA256" --journal
```

Классификатор использует отрезок до последнего подтверждённого сигнала. Открытый инцидент, отсутствие конца или разрыв внутри этого отрезка дают `unknown`. Если агрегаты подтверждают прикладную деградацию, возвращается `unknown` с указанием причины. При оценке известных типов считайте пропуски детектора и отказы классификатора в знаменателе recall. Порог уверенности подбирается отдельно для каждой метки по ошибкам на калибровочных эпизодах. Тип, который модель ни разу не распознала при калибровке, остаётся недоступен до появления новых примеров.

## Раздельный журнал v4

Выставьте `NETWATCH_POLICY_VERSION=v4` в профиле стенда или теневого запуска. Окна и предсказания продолжают идти через Go, PostgreSQL и Python. Поля `status`, `score` и `threshold` описывают сетевую модель. Поле `http` содержит независимое состояние и причину HTTP-правила. Отсутствие измерения отличается от штатной работы. У старых политик остаётся прежний общий сигнал.

В v4 сетевой сигнал и HTTP-сигнал открывают и закрывают свои инциденты. В карточке и API есть поле `evidence_channel`. Два связанных по времени инцидента могут иметь разный источник и разные границы. Хеш Random Forest закрепляют один для обоих детекторов одного сервиса. В типизации подтверждённый HTTP-сбой остаётся неизвестным сетевым типом. Сетевой эпизод с собственной пригодной телеметрией типизируется независимо.

Пример преобразования доверенных пятисекундных агрегатов прокси за период отсутствия пакетного сенсора. Границы заданы как UTC epoch в наносекундах и выровнены на 5 секунд. Эпоха должна быть уникальной для заявленного наблюдения. Применяйте на период, где пакетное окно отсутствует. Команда читает только каталог агрегатов и выводит JSONL. Пакетные значения остаются `null`.

```sh
go build -o ./bin/netwatch-sensor ./cmd/netwatch-sensor
./bin/netwatch-sensor context --input "$PROXY_AGGREGATES" --service "$TCP_SERVICE" \
  --sensor "$SENSOR_ID" --epoch "$OUTAGE_EPOCH" --feature-set traffic-v2 \
  --start-ns "$START_NS" --end-ns "$END_NS" > "$OUTPUT_JSONL"
./bin/netwatch-sensor enqueue --spool "$SPOOL_DIR" --input "$OUTPUT_JSONL"
./bin/netwatch-sensor send --spool "$SPOOL_DIR" --endpoint "$WINDOWS_API"
```

Калибруемый независимый режим обучения для v4 задаёт в манифесте `"independent_application_evidence": true` и запускает обучение обоих детекторов с `--rules`. Приложение выдаёт подтверждённый сигнал из агрегатов даже при потере пакетов, если объём измерения соответствует порогам HTTP. Единицы, источник и выборка для HTTP-порогов должны совпадать у обоих вариантов. Кандидат требует закрытой приёмки до назначения рабочим профилем.

### Подготовить агрегаты из журнала прокси

Для контролируемого повтора используйте `scripts/aggregate_http_context.py`. На входе JSONL завершённых запросов одного сервиса. Поля каждой записи `completed_at_ns`, `route_id`, `method`, `status`, `latency_ms`, `request_body_bytes`, `response_body_bytes`. Размеры тела могут быть `null`. Приведите маршрут к стабильному имени из конфигурации приложения. Размеры берите из измерений прокси или приложения. TCP-байты содержат заголовки и повторные передачи и для этого поля не подходят.

```sh
python3 scripts/aggregate_http_context.py "$COMPLETED_REQUESTS" "$PROXY_AGGREGATES" \
  --sensor "$SENSOR_ID" --entity "TCP/$TCP_SERVICE" --start-ns "$START_NS" --end-ns "$END_NS" \
  --planned "$VERIFIED_SCHEDULE" --expectations "$KNOWN_DEMAND" --source "$LOG_BATCH_ID" \
  --group-id "$NETWATCH_APPLICATION_CONTEXT_GID"
```

Границы обозначают подтверждённую полноту логов. Только внутри такого интервала отсутствие записей означает ноль завершений. `--planned` принимает упорядоченный JSON-массив интервалов `start_ns` / `end_ns`, выровненных по пяти секундам. Опустите его при неизвестном расписании. `--expectations` принимает JSONL с `window_start_ns`, `as_of_ns`, `route_id`, `method`, `expected_requests`. Прогноз должен быть зафиксирован к началу своего окна. При отсутствии независимой оценки опустите этот аргумент. Статус плановой операции, разметка аномалии и фактическое число завершений не используются как прогноз спроса.

Для числовых признаков операций детектора включите `operation_context: true` при подготовке нового артефакта. Старые записи с базовым HTTP-контекстом используют профиль без этого параметра. Дополнительные признаки Random Forest включаются через `episode_classifier_version: 5`. Проверяйте обе модели на одних захватах. Отказ от сетевого типа измеряйте отдельно от штатного отказа HTTP-правила на прикладной деградации.
